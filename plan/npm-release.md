# npm release automation

Goal: publish `@caperjs/*` to the public npm registry on an automated, repeatable
schedule, so consumers (starting with bankshot-web) resolve caper from a registry
instead of a `link:` override pointing at a sibling working copy.

Model: **Changesets in `fixed` mode.** All packages continue to share one version
number, exactly as `scripts/update-package-versions.mjs` enforces today. Changesets
replaces that script, adds changelogs, and adds a canary channel.

Version line: **reset to `0.1.0`.** The current 6.2.x numbering is inherited from
the upstream fork, not earned. See "Resetting the version line" below.

Scope: **`@caperjs`.** `@caper` was unavailable. See P1 below.

---

## Why this model

- Six packages that always move together. `fixed` mode encodes the lockstep rule
  that is currently implicit in a bespoke script.
- Conventional commits are already enforced (`commitlint` + husky `commit-msg`),
  but commit messages alone are a poor changelog for a framework. A changeset file
  per user-visible change gives better release notes for the same effort.
- The canary channel is the real prize. A fast-moving framework with one consumer
  needs "publish this branch as an installable version right now" more than it
  needs release ceremony.
- Changesets is the default choice for pnpm monorepos (pnpm itself, Astro, Remix,
  Radix all use it), so the failure modes are well documented.

Rejected: `semantic-release` (monorepo support is community plugins, and no human
gate before a release ships), independent versioning (six version lines to reason
about for no benefit at this size), tag-and-publish only (no changelogs).

## Resetting the version line

caper was forked from [dill-pixel](https://github.com/relishinc/dill-pixel) and has
diverged substantially. The inherited 6.2.x numbering is upstream's, not caper's:
`dill-pixel` on npm is at 6.2.3, which is exactly this repo's root version.
Publishing a brand new package at 6.2.3 would imply six major versions of history
that do not exist under this name.

**Reset to `0.1.0`.** This is free:

- Zero git tags in the repo (verified), so nothing to reconcile or delete.
- Nothing has ever been published under `@caper`, so there is no npm version floor.
  npm only forbids publishing *below* an existing version of the *same package name*.
- `packages/core/src/version.ts` is auto-generated by `scripts/generate-version.mjs`
  at build time, so it self-corrects. No hand editing.

Not `0.0.0`: it is publishable but conventionally reads as "nothing here", and
Changesets snapshot releases already use `0.0.0-<tag>-<sha>` as their base version.
Having a real 0.0.0 release alongside that is needlessly confusing.

### Semver rules while pre-1.0

Under 0.x the ecosystem convention, which Changesets and npm range resolution both
assume, is shifted down one slot:

| Change | Bump | Example |
| --- | --- | --- |
| Breaking | minor | 0.1.0 to 0.2.0 |
| Feature | patch | 0.1.0 to 0.1.1 |
| Fix | patch | 0.1.0 to 0.1.1 |

Never select `major` in a changeset until 1.0 is a deliberate decision.

The practical consequence is good for a fast-moving fork: `^0.1.0` resolves only to
`0.1.x`, **not** `0.2.0`. Consumers can never silently pick up a breaking change.
The cost is that bankshot-web needs an explicit range bump on every breaking
release, which is the correct amount of friction right now.

Reach 1.0 when the public API stops changing shape, not on a date.

### Files to touch

Root `package.json`, all six `packages/*/package.json`, and
`apps/kitchen-sink/package.json`. Nothing else hardcodes a version.

Do this in the same commit as the P1a scope rename. One commit, one clean break
from the fork's inherited identity.

## Preconditions to settle first

### P0. Licensing, blocking for a public publish

Upstream `dill-pixel` is **MIT**. This repo currently has:

- no `LICENSE` file at all, and
- `"license": "ISC"` in the root `package.json`, with an empty `author` field.

MIT requires the original copyright and permission notice be preserved in
derivative works. Publishing publicly to npm makes this a real obligation rather
than a formality. Fix before the first publish:

1. Add a `LICENSE` file with the MIT text, retaining the upstream Relish
   Interactive copyright line and adding your own beneath it.
2. Change `license` to `"MIT"` in the root and in all six packages.
3. Fill in `author`, `description`, and `keywords`, and add
   `repository.directory` to each package so npm pages link to the right subtree.
4. Keep the fork attribution that is already in the READMEs.

### P1. Scope: `@caperjs` (RESOLVED)

The `@caper` scope was not available: a dormant unscoped `caper` package (0.0.2,
"Just-in-time HTTP server", untouched since 2022) holds the name. A name dispute
was rejected as a plan, since npm's policy is that abandonment alone does not
justify a transfer.

`@caperjs` was briefly assumed blocked for the same reason, because an unscoped
`caperjs` package also exists (2.1.3, "Use jumping text", dormant since 2022).
That assumption was wrong: an existing package name does not prevent an org of
the same name, and the `caperjs` org was already owned by `anthonysappdev`.

**Scope is `@caperjs`.** Packages become:

| Old | New |
| --- | --- |
| `@caper/core` | `@caperjs/core` |
| `@caper/plugin-colyseus` | `@caperjs/plugin-colyseus` |
| `@caper/plugin-crunch` | `@caperjs/plugin-crunch` |
| `@caper/plugin-firebase` | `@caperjs/plugin-firebase` |
| `@caper/plugin-google-analytics` | `@caperjs/plugin-google-analytics` |
| `@caper/plugin-rive` | `@caperjs/plugin-rive` |
| `@caper/plugin-rollbar` | `@caperjs/plugin-rollbar` |

The repo, the framework, and the CLI stay named "caper". Only the npm scope changes.

### P1a. Rename the imports, do not alias

The alternative was publishing as `@caperjs/*` while keeping `@caper/core` as
the import specifier via a `npm:` alias in each consumer:

```json
"@caper/core": "npm:@caperjs/core@^0.1.0"
```

**Rejected.** An alias means two names for one package permanently, in the docs, in
every app the CLI scaffolds, and for anyone who installs `@caperjs/core` and
then finds they must import `@caper/core`. The rename is a one-time mechanical
change and this is the cheapest moment it will ever be: pre-1.0, no external users,
and the version line is being reset in the same breath.

Scope of the rename:

- **caper repo:** 87 files reference `@caper/`, including `packages/*/package.json`
  dependency entries, `apps/kitchen-sink`, the CLI templates under
  `packages/core/templates`, and the docs.
- **bankshot-web:** 84 files, all importing `@caper/core` only, plus the two
  dependency entries and the two `overrides` entries in `pnpm-workspace.yaml`.

Both repos must land the rename together, in lockstep with the Phase 1 publish.

**Verification:** `tsc --noEmit` clean in both repos, and
`grep -r "@caper/" --exclude-dir=node_modules` returns nothing but changelog and
plan-document history.

### P2. Repo hygiene, needed before Changesets runs

Four issues found in the current tree:

1. **Root `caper-main` is not `private: true`.** Changesets will attempt to version
   and publish it. A stray `npm publish` at the root would too. Set it private.
2. **`apps/kitchen-sink` is not `private: true`.** Same problem. Set it private.
3. **Version drift, moot after the reset.** Root is `6.2.3` and the packages are
   `6.2.2`, but the reset to `0.1.0` collapses both. Just make sure every file in
   "Files to touch" above lands on the same number in one commit.
4. **`workspace:*` rewriting.** Cross-package deps use `workspace:*`.
   `pnpm publish` rewrites those to real versions on pack; `npm publish` does not,
   which is the entire reason `scripts/publish-packages.mjs` exists. Changesets
   invoking pnpm is expected to handle this natively. **Verify with a dry run
   before deleting that script** (see Phase 3 verification).

## Phase 1: publish once, by hand

Establish a real baseline and prove the consumer story works before adding any
automation on top.

1. Settle P0 (license).
2. One commit: rename the scope to `@caperjs/*` per P1a **and** set every
   version to `0.1.0` per "Files to touch" above.
3. `pnpm packages:build && pnpm framework:build`. Confirm `generate-version.mjs`
   rewrote `packages/core/src/version.ts` to `0.1.0`.
4. `pnpm publish --access public` from each package directory (use pnpm, not npm,
   so `workspace:*` is rewritten). Scoped packages default to restricted access, so
   `--access public` is load-bearing on the very first publish of each package.

**Verification:** in a scratch directory outside both repos,
`pnpm add @caperjs/core@0.1.0` succeeds and the tarball contains `lib/`,
`types/`, `templates/`, and `client.d.ts` per the `files` array.

**Then, in bankshot-web:** apply the P1a rename across its 84 files, change the two
dependency entries to `@caperjs/core` and
`@caperjs/plugin-google-analytics` at `^0.1.0`, delete both entries from
`overrides` in `pnpm-workspace.yaml`, `pnpm install`, and confirm `tsc --noEmit`,
`pnpm build`, and the reducer suite all pass against the registry copy. This is the
step that actually unblocks off-laptop builds (Cloudflare, CI, fresh clones).

### What actually happened

Shipped as 0.1.1, not 0.1.0. Five things the plan did not anticipate:

1. **`zod` was in core's `devDependencies`** while the shipped `config/vite.mjs`
   imports it. Consumers got whatever stray zod was hoisted (v3) and crashed with
   `z.object(...).loose is not a function`. Linking hid this completely, because
   caper's own `node_modules` had zod 4. Moved to `dependencies` in 0.1.1.
   **Lesson: publishing is the only thing that catches dev/prod dependency errors.**
   A scan of shipped `config/`, `cli/`, `lib/`, `templates/` for undeclared imports is
   worth repeating before any future first-publish.
2. **`@caperjs/plugin-rive@0.1.0` published into a ghost state**: reported success,
   listed by `npm access` as public, but 404 on the read path forever, and
   unrepublishable. 0.1.1 resolved it. If this recurs, bump the version, do not fight it.
3. **Publishing needs a granular token with Bypass 2FA.** A `npm login` token only
   yields an OTP prompt. The token lives in caper's gitignored `.npmrc`. Phase 2
   removes the need for it entirely.
4. **`.pnpmfile.cjs` contaminates the lockfile.** bankshot-web already had a
   `CAPER_LINK=1` overlay, which is a better mechanism than the deleted `overrides`
   block, but pnpm persists the rewritten spec into `pnpm-lock.yaml`. A lockfile
   generated under `CAPER_LINK=1` breaks CI exactly the way the overrides did.
   Recovery is awkward: plain `pnpm install` says "Already up to date" and refuses to
   re-resolve; `pnpm add "@caperjs/core@^x.y.z"` forces it.
5. **pnpm 11's publish-age gate blocks fresh releases.** It auto-wrote pinned
   `minimumReleaseAgeExclude` entries for the exact versions installed. Replaced with
   a `'@caperjs/*'` pattern in bankshot-web, otherwise every future release, and every
   Phase 4 canary, is gated until it ages.

**CI verified:** a `--frozen-lockfile` install in a clean directory with no caper
checkout, no `HOME`, and no npmrc succeeds and pulls 0.1.1 from the registry.
`pnpm build` under CI is still untested; AssetPack over the raw asset tree is a much
bigger surface than dependency resolution.

Still open: `src/core/interfaces/IApplication.ts:37` has a JSDoc example importing
from `@caperjs/framework`, which is not a real package.

## Phase 2: trusted publishing

Configure npm's OIDC trusted publishing before automating, not after.

- No `NPM_TOKEN` secret stored anywhere. GitHub Actions mints a short-lived
  credential per run.
- Publishes get provenance attestations automatically, which show as a verified
  badge on npmjs.com.
- Requires: each package configured on npmjs.com with a trusted publisher pointing
  at `anthonysapp/caper` and the release workflow filename; the workflow needs
  `permissions: { id-token: write, contents: write }`.

**Verification:** a manual workflow dispatch publishes a patch and the npm page
shows the provenance badge.

Fallback if trusted publishing cannot be configured for all six packages: a
granular automation token scoped to the `@caper` org, stored as a repo secret, with
an expiry reminder. Classic tokens are not an option.

## Phase 3: Changesets

1. `pnpm add -Dw @changesets/cli && pnpm changeset init`.
2. Configure `.changeset/config.json`:
   - `fixed`: one group listing all six packages, so they version in lockstep.
   - `ignore`: `caper-kitchen-sink` (belt and braces alongside `private: true`).
   - `access: "public"`, `baseBranch: "main"`.
   - Leave `privatePackages` alone; `private: true` from P2 keeps the root and
     kitchen-sink out.
3. Add the `changesets/action` release workflow: on push to `main`, it either opens
   or updates a "Version Packages" PR, or, if that PR was just merged, runs the
   build and publishes.
4. Wire `turbo build` as the release `build` step so publish never ships a stale
   `lib/`.
5. Retire `scripts/update-package-versions.mjs` and `scripts/publish-packages.mjs`,
   plus the `packages:update` / `packages:publish` / `packages:all` /
   `build-publish-all` npm scripts that call them.

Note: `update-package-versions.mjs` also pins `pixi.js`, `@pixi/sound`, `vite`, and
`vite-plugin-dts` across packages from `packages/core`'s values. Changesets does
**not** do that. Either keep a trimmed version of the script for third-party pins
and drop only its `@caperjs/core` and `version` handling, or move those pins to a
pnpm `catalog:` in `pnpm-workspace.yaml`. Catalogs are the better long-term answer
and are a one-time edit.

**Verification:**
- `pnpm changeset version` on a scratch branch bumps all six packages to the same
  number and rewrites inter-package ranges correctly.
- `pnpm publish --dry-run` from `packages/plugin-google-analytics` shows
  `@caperjs/core` resolved to a real version, not `workspace:*`. This is the check
  that justifies deleting `publish-packages.mjs`.

## Phase 4: canary channel

A separate workflow, `workflow_dispatch` plus optional push-to-branch trigger:

```
pnpm changeset version --snapshot canary
pnpm changeset publish --tag canary --no-git-tag
```

Produces versions like `0.0.0-canary-<sha>` published under the `canary` dist-tag,
so `latest` is never affected and nothing lands in the changelog.

Consumers pin the exact version:

```json
"@caperjs/core": "0.0.0-canary-a1b2c3d"
```

The `0.0.0` base is why the stable line starts at `0.1.0` rather than `0.0.0`.

**Verification:** publish a canary, install it in bankshot-web, confirm
`npm view @caperjs/core dist-tags` still points `latest` at the stable
release.

## Day-to-day flow after this lands

- **Normal change to caper:** commit as usual, run `pnpm changeset` before merging,
  pick minor for breaking or patch for everything else (see the 0.x table), write
  one line of user-facing description. Merge to main. The bot opens a Version
  Packages PR. Merge it when you want to ship.
- **Need an unreleased caper in bankshot-web off-laptop:** trigger the canary
  workflow, pin the exact canary version in bankshot-web.
- **Tight local iteration on caper:** keep using a `link:` override, but do it in a
  way that is not committed. `pnpm-workspace.yaml` is tracked, so the current
  approach cannot stay. Options to decide separately: `pnpm link` and `pnpm unlink`
  as a manual toggle, or accept the canary loop as the only cross-repo path.
