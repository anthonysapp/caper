## Phase 8 — Typed factory revamp (§8 nice-to-have, promoted)

Before the revamp, four different init patterns coexisted: scenes loaded by id (typed), plugins by id (typed), popups by id with untyped config, and entities via a two-phase `new Entity(); this.add.existing(entity, props)` dance with zero type fidelity. Discovery was already walking every scene/popup/entity file and AST-parsing the class — the DX cost of that walk was being paid, but the typed-factory payoff wasn't being collected. This phase collects it: one coherent `(id, props)` shape across entities, popups, and scenes, driven entirely by `typeof import(path).default` codegen + standard TypeScript helpers (no AST type extraction).

- [x] **`typeof import()` codegen** — `generateTypes()` in [config/vite.mjs](../packages/core/config/vite.mjs) gained three new slots in the emitted `AppTypeOverrides` augmentation: `SceneClasses`, `PopupClasses`, `EntityClasses`. Each is a `{ [id]: typeof import('@/.../Foo').default }` map built via a new `buildClassMap(items)` helper that only emits active entries and skips items without an `importPath`. Paths use the same `@/` alias the discovery already emits, so they resolve through the consuming project's `tsconfig.paths`. The generated file also now emits `type AppSceneClasses`, `type AppPopupClasses`, `type AppEntityClasses` as named aliases — they're the payload for each slot.
- [x] **Entity imports flipped to eager by default** — `discoverLocalClassFiles` gained a `defaultDynamic` parameter; `discoverEntities` passes `false` so entities become static imports at the virtual-module level unless `defineEntity({ dynamic: true })` explicitly opts into code-splitting. Required so `this.add.entity(id, props)` can synchronously instantiate without `await` in scene init. Popups and scenes stay dynamic (their APIs are async anyway).
- [x] **Scene discovery now carries `importPath`** — the scenes array used to lack `importPath` on its items (only internal-scoped). Added `importPathForTypes` (extension-stripped) so `buildClassMap` can emit scene entries the same way it does for popups and entities.
- [x] **Framework-side helper types** ([src/utils/types.ts](../packages/core/src/utils/types.ts)) — `EntityId`/`EntityCtor`/`EntityProps`/`EntityInstance`, `PopupId`/`PopupCtor`/`PopupProps`/`PopupInstance`, `SceneId`/`SceneCtor`/`SceneProps`/`SceneInstance`/`SceneLoadArgs`. All derive via `ConstructorParameters<>` + `InstanceType<>` + `infer` from the `_EntityClassMap`/`_PopupClassMap`/`_SceneClassMap` conditional types that read the `AppTypeOverrides` augmentation. `SceneLoadArgs<K>` collapses to `[]` when `SceneProps<K>` is `void` (scenes without the generic) and to `[props: SceneProps<K>]` otherwise — enables the overloaded `loadScene<K>(id, ...args)` signature where unparameterized scenes call `loadScene('menu')` with no second arg.
- [x] **Entity factory runtime registry** ([src/mixins/factory/registry.ts](../packages/core/src/mixins/factory/registry.ts)) — lazy module-level map populated on first lookup from `globalThis.Caper.get('entityList')` (same pattern `SceneManagerPlugin` already uses for `sceneList`). Dynamic-import entries (arrow functions without `prototype`) are skipped because the factory is sync — if a project needs code-split entities, they fall back to `add.existing(new Foo(...), props)` with a manual lazy import. Exposes `getEntityCtor(id)` and `getRegisteredEntityIds()` (the latter used for fail-loud error messages on unknown ids). Vitest coverage in [registry.test.ts](../packages/core/src/mixins/factory/registry.test.ts): static-import registration, inactive filtering, dynamic-import skip, unknown id returns undefined, missing globalThis.Caper handled gracefully, caching after first lookup.
- [x] **`entity` factory method** added to `defaultFactoryMethods` ([src/mixins/factory/const.ts](../packages/core/src/mixins/factory/const.ts)). Signature `<K extends EntityId>(id: K, props?: EntityProps<K> & EntityFactoryProps) => EntityInstance<K>`. Looks up the class via `getEntityCtor`, fails loud with `[caper] Unknown entity id 'x'. Known: ...` listing the known ids if not registered, then `new Ctor(props)`. After construction the factory applies layout-ish props (`position`/`x`/`y`/`scale`/`pivot`/`alpha`/`visible`) via the existing `resolvePosition`/`resolveScale`/`resolvePivot` helpers — mirrors how `this.add.existing` works so `this.add.entity('actor', { color, x, y })` reads naturally. `EntityFactoryProps` is a new narrow interface in [props.ts](../packages/core/src/mixins/factory/props.ts) that's deliberately *without* the `AbstractProps` index signature — preserves typo enforcement on entity-specific props at the call site.
- [x] **Optional `Entity<Props>` base class** at [src/display/Entity.ts](../packages/core/src/display/Entity.ts). Extends `Container`, stores `props` in the constructor as `readonly`. Not required — plain `Container`-extending entities still work with the factory as long as they follow the single-options-object constructor convention. The base class exists so entity authors who want typed prop storage + a canonical lifecycle can opt in.
- [x] **`Scene<Props>` generic** ([src/display/Scene.ts](../packages/core/src/display/Scene.ts)) — `public props!: Props` field, populated by `SceneManagerPlugin._createCurrentScene` before `initialize()` fires. Non-parameterized scenes default to `Scene<void>` so `app.scenes.loadScene('menu')` still takes no second arg. `SceneLoadArgs<K>` handles the overload wiring: for `K = 'menu'` (Scene<void>) it collapses to `[]`, for `K = 'level'` (Scene<LevelProps>) it expands to `[props: LevelProps]`.
- [x] **`SceneManagerPlugin.loadScene` overloaded** — new `loadScene<K extends SceneId>(id: K, ...args: SceneLoadArgs<K>)` added alongside the existing loose `LoadSceneConfig | string` overload. Internal `_pendingLoadProps` field buffers the typed props and `_createCurrentScene` assigns them onto `this.currentScene.props` right after `new SceneClass()`, then clears the buffer. The hash-based sidebar loader goes through the loose overload (which accepts any string), so bare `loadScene('level')` via hash keeps working — parameterized scenes handle missing props with a runtime default at the scene level. Positive typed enforcement still catches wrong prop types, unknown enum values, and unknown scene ids at compile time.
- [x] **`Application.loadScene` overloaded** to match, with a runtime impl that forwards args to the scene manager via a type-assertion cast (the runtime is fully generic — only the type signature needs the split).
- [x] **`ICoreFunctions` interface updated** ([src/core/interfaces/ICoreFunctions.ts](../packages/core/src/core/interfaces/ICoreFunctions.ts)) — both `loadScene` (typed + loose overloads) and `showPopup` (replaces the old `addPopup` + `showPopup<T>` pair) got the new typed signatures. Drops `addPopup` entirely: popups register themselves from discovery now.
- [x] **Popup auto-registration + typed `showPopup`** ([src/plugins/PopupManagerPlugin.ts](../packages/core/src/plugins/PopupManagerPlugin.ts)) — `initialize()` now pulls the popup list off `globalThis.Caper.get('popupList')` (populated by `caper-runtime` before Application starts) and seeds `this._popups` automatically. Entries stay as dynamic-import functions until first `showPopup()` resolves and caches the real constructor via a new `_resolvePopupCtor(id)` helper. The public `addPopup` method is gone — discovery is the registry now. `showPopup<K extends PopupId>(id, config?)` gets the new typed signature deriving `config` from `PopupProps<K>` (constructor param [1] of the popup class, so subclasses that declare `class MyPopup extends Popup<MyData>` flow `config.data` through to the call site). A `show` alias forwards to `showPopup` for brevity at call sites like `this.app.popups.show('confirm', {...})`.
- [x] **`Popup<T>` base class** ([src/ui/Popup.ts](../packages/core/src/ui/Popup.ts)) — constructor `config` param tightened from `Partial<PopupConfig>` to `Partial<PopupConfig<T>>` so the generic `T` actually narrows `config.data` at instantiation sites. Was already declared generic at the class level but the constructor param wasn't carrying the generic through, so the type-fidelity was one link short of useful.
- [x] **Kitchen-sink entity migration** — [Actor.ts](../apps/kitchen-sink/src/entities/Actor.ts) `constructor(private color: number = 0xffffff)` → `constructor(props?: ActorProps)` with `this.color = props?.color ?? 0xffffff`. [Boy.ts](../apps/kitchen-sink/src/entities/Boy.ts) / [Dragon.ts](../apps/kitchen-sink/src/entities/Dragon.ts) / [Player.ts](../apps/kitchen-sink/src/entities/Player.ts) got matching no-op `constructor(_props?: {})` signatures to conform to the single-options-object convention. Player specifically was rewritten as `class Player extends Entity<PlayerProps>` to exercise the new optional base class end-to-end.
- [x] **FocusScene call sites updated** — `new Actor(); this.actorList.add.existing<Actor>(...)` → `this.actorList.add.entity('actor', { color })`. The `accessibleTitle`/`accessibleHint`/`layout` props that FocusScene was funneling through `add.existing` get set post-hoc on the returned instance, which is cleaner than widening `EntityFactoryProps` to a `{ [key: string]: any }` passthrough (that widening would've swallowed typo errors — not worth it).
- [x] **PopupScene migrated** — removed the three `this.app.popups.addPopup('one'/'two'/'three', ExamplePopup)` calls (discovery replaces them), updated the three buttons to all reference the discovered `example` popup id with different config variants + added a fourth button for the `confirm` popup. Inner `showPopup` helper now types `popupId` as `PopupId` instead of `string | number`. `this.app.func.showPopup(popupId, config)` still works because `showPopup` is still on `ICoreFunctions` — only the internal registration flow changed.
- [x] **`KitchenSinkApplication` updated** — `this.popups.showPopup(detail.id, detail.data)` gained a `detail.id as PopupId` cast (the `show_popup` action's detail is `string | number` from the action typing; the popup id union is `string`-only, so the cast narrows at the call site). Minimal change, no broader action-typing refactor.
- [x] **LevelScene demo** ([apps/kitchen-sink/src/scenes/framework/LevelScene.ts](../apps/kitchen-sink/src/scenes/framework/LevelScene.ts)) — `class LevelScene extends Scene<LevelProps>` with `{levelId: number, difficulty: 'easy'|'normal'|'hard'}`. Displays the current props in a text label. `start()` wires `1`/`2`/`3` keys to typed `loadScene('level', {...})` calls — positive demo of the typed overload. `initialize()` falls back to `DEFAULT_LEVEL_PROPS` if `this.props` is undefined so hash-loaded entries don't crash.
- [x] **Negative-test coverage (manual)** — verified via an ephemeral test file that wrong prop types (`levelId: '3'` instead of number), unknown enum values (`difficulty: 'medium'`), and unknown scene ids (`loadScene('levelll')`) all error at compile. The "missing props entirely" case falls through to the loose `loadScene(sceneIdOrLoadSceneConfig: LoadSceneConfig | string)` overload because TypeScript's overload resolution picks the loose match when the typed overload's tuple constraint fails — accepted tradeoff since removing the loose overload would break the framework's internal `_listenForHashChange` handler that passes bare `string`.
- [x] **Vitest coverage** — [registry.test.ts](../packages/core/src/mixins/factory/registry.test.ts), 6 cases covering the in-memory registry paths. Skipped a separate `Entity.test.ts` because `Entity extends Container → mixins → factory/const.ts → display/index.ts → Scene → Container` is a pre-existing circular-ish import chain that happens to be load-order-fragile outside production bundling: instantiating `Entity` in a test hits `Class extends value undefined is not a constructor` on Scene's `extends Container`. Not worth the mock-gymnastics to dismantle for a 10-line class; the registry test covers the interesting logic and the kitchen-sink build is the real integration test.
- [x] **JSDoc** — Scene base class lifecycle doc updated to explain the new `props` field and how it flows from `loadScene(id, props)` through `_createCurrentScene` → `initialize()`. Entity base class has a full `@example` showing the convention. `PopupManagerPlugin.showPopup` + `ICoreFunctions.showPopup` document the typed-id + typed-config flow and how `Popup<T>`'s generic narrows `config.data`.
- [x] **Verification**:
  - `pnpm framework:build` clean (unchanged pre-existing `Plugin.test.ts` TS2554 warning, untouched).
  - `pnpm kitchen-sink:build --force` — 7/7 tasks, 5.3s. Generated [caper-app.d.ts](../apps/kitchen-sink/src/types/caper-app.d.ts) contains populated `AppSceneClasses` (21 entries), `AppPopupClasses` (2), `AppEntityClasses` (4).
  - `pnpm --filter @caper-engine/core test` — 29/29 passing (23 pre-existing + 6 new registry).
  - Kitchen-sink tsc clean across all new call sites. Pre-existing errors unrelated to this phase (CaperButton.label type mismatch, Runner active accessor conflict, caper-runtime virtual module, TS6133 unused-var warnings) left as-is.

**Landmines defused**:
- `_EntityClassMap`/`_PopupClassMap`/`_SceneClassMap` conditional types default to `Record<string, never>` when `AppTypeOverrides` isn't augmented (framework built in isolation or no entities discovered). The derived helpers degrade to `never`/`string` cleanly.
- `typeof import()` emits for entities/popups/scenes use `@/...` aliased paths — tsc `tsconfig.paths` resolution applies because the generated `.d.ts` lives inside the consuming project's compile unit.
- `ConstructorParameters<...>[0]` with optional params gives `T | undefined`; switched to `ConstructorParameters<typeof X>[0]` (via the `AnyCtor` shape constraint) which plays nicer with optional single-arg constructors and mixin-wrapped classes.
- Turbo caches `kitchen-sink:build` output including the generated `caper-app.d.ts` — had to `--force` a few times to verify new codegen during iteration. Worth noting for future type-gen changes.
- TypeScript's overload resolution tries overloads in declaration order and picks the first match. The typed `loadScene<K>` overload is first; if its tuple constraint can't be satisfied (missing props), TS falls to the loose string overload rather than erroring. This is by design here because the framework's own hash loader relies on the loose overload accepting bare strings.

## Phase 9 — Schema-driven factory registry

Phase 8 added `this.add.entity` to the factory surface but left the other 17 factory methods in their original hand-written form — each one independently doing the construct → resolve-position → resolve-scale → resolve-pivot → resolve-anchor → passthrough-unknowns dance, with ~15 lines of copy-paste boilerplate per method. Adding a new factory method meant writing ~15 lines of near-identical plumbing. Worse, inconsistencies had accumulated: `animatedSprite` carried a copy-pasted `['x', 'y', 'position', 'text', 'roundPixels', 'resolution', 'style', ...]` exclude list that was nonsensical for AnimatedSprite (`text`/`style`/`resolution` aren't AnimatedSprite fields — copy-paste residue from `text`). Phase 9 collapses all of this into a schema-driven registry where each method is a tiny declarative entry: the bespoke `build` callback + a list of which common resolvers to apply + a list of keys the build consumed. The helper does the rest.

- [x] **`buildFactoryMethod(schema)` helper** ([packages/core/src/mixins/factory/schema.ts](../packages/core/src/mixins/factory/schema.ts)) — single generic function that takes a `FactorySchema<Props, Instance>` and returns a typed `(props?: Props) => Instance` method. The schema has three fields: `build: (props?) => Instance` (the bespoke constructor call, including any DX reshaping like Sprite's asset-name resolution or Text's style-flattening), `applies?: FactoryApply[]` (which of `position`/`scale`/`pivot`/`anchor` to run post-construct), and `exclude?: readonly string[]` (keys the build already consumed, excluded from the unknown-keys passthrough alongside the auto-excluded resolver keys). The helper centralizes: calling `build`, routing position/scale/pivot/anchor to their resolvers, and forwarding remaining keys via `resolveUnknownKeys`.
- [x] **Direct-source imports to dodge circular chains** — `schema.ts` imports `omitKeys` from `../../utils/object` rather than via the `../../utils` barrel, because the barrel transitively pulls in `types.ts` → `display/Scene` → `display/index.ts` → `Container` → `Factory()` → `const.ts` (which imports from `schema.ts`), and vitest's module evaluator doesn't tolerate the cycle. The cycle is fine in bundled builds because esbuild handles it, but the runtime test environment hits it first. Documented in a comment on the import line so the next maintainer doesn't "clean it up" back to the barrel.
- [x] **14 schema-driven methods** ([packages/core/src/mixins/factory/const.ts](../packages/core/src/mixins/factory/const.ts)) — `container`, `particleContainer`, `sprite`, `tilingSprite`, `animatedSprite`, `graphics`, `text`, `htmlText`, `bitmapText`, `button`, `flexContainer`, `uiCanvas`, `spine` all migrated to `buildFactoryMethod({ build, applies, exclude })` entries. `spineAnimation` stays hand-written to preserve the `<ANames extends string>` generic (kitchen-sink's `SpineScene` uses `this.add.spineAnimation<CharacterAnimations>({...})` for typed animation names — the helper can't carry that generic through). `existing`, `texture`, `toaster`, `svg`, `entity` stay hand-written because their signatures don't fit the `(props?) → instance` shape (2-arg, required-field, or plain resolver re-bind).
- [x] **Text-family consumed-keys constant** — extracted `TEXT_CONSUMED_KEYS = ['text', 'roundPixels', 'resolution', 'style', 'anchor', 'pivot']` so the three text schemas (`text`, `htmlText`, `bitmapText`) share it instead of drifting apart. `bitmapText` technically doesn't consume `resolution` since Pixi's BitmapText ctor doesn't take it, but including it in the exclude list is a no-op — preserves the single source of truth.
- [x] **Explicit return type annotations on Caper-class build callbacks** — the schema helper originally inferred `Instance` from the `build` callback's return expression. This worked for methods returning Pixi classes (`new Sprite()`, `new Graphics()`) because Pixi's types don't have cycles. It **failed** for methods returning Caper display classes (`new Container()`, `new Button()`, `new AnimatedSprite()`, etc.) because resolving those types requires the Factory mixin, which requires `typeof defaultFactoryMethods`, which is circular with the schema being defined. The original hand-written methods dodged this by using inline arrow function bodies where TypeScript does lazy return-type inference; the new schema form triggered eager generic resolution and blew up. Fix: add an explicit return type on each Caper-class `build` callback (`build: (props?) : Container => new Container(...)`). TypeScript treats return-type annotations on arrow function parameters with the same lazy resolution as inline inference, and the cycle never triggers. Pixi-class methods (`sprite`, `tilingSprite`, `graphics`, `text`, `htmlText`, `bitmapText`) don't need the annotation.
- [x] **`UICanvasProps` cast** — UICanvas's constructor takes `Partial<UICanvasProps>` (a superset of `UICanvasConfig`), but `pluck(props, UICanvasConfigKeys)` narrows to `Partial<UICanvasConfig>`. The old hand-written method silently relied on TypeScript's structural compatibility; the schema version surfaced the mismatch. Added an explicit `as Partial<UICanvasProps>` cast in `build` with a comment explaining the superset relationship.
- [x] **Verification**:
  - `pnpm framework:build` clean. Generated `packages/core/lib/mixins/factory/const.d.ts` shows every migrated method with its exact concrete return type (`container: (props?: Partial<ContainerProps> | undefined) => Container;` etc.) — no `any` leaks, no `unknown`, no generic fallouts.
  - `pnpm kitchen-sink:build --force` — 7/7 tasks, 5.2s. The kitchen-sink uses every migrated method across its scenes; build-time inference + runtime dispatch both work end-to-end.
  - `pnpm --filter @caper-engine/core test` — 29/29 passing (same count as Phase 8). Deliberately skipped a dedicated `schema.test.ts` unit suite because importing `buildFactoryMethod` from a test file pulls in `factory/utils.ts` which pulls in `../../utils` (barrel) which pulls in `display/Container` which hits the Factory cycle at vitest module-eval time. Rather than introduce a parallel resolver file just to break the cycle, schema coverage stays implicit via the kitchen-sink build — every method the schema helper produces is exercised by at least one real scene there.

**Line count shift**: const.ts is roughly the same size pre/post refactor (~340 lines) because the JSDoc I added is substantial. But the **per-method footprint** shrunk from ~15 hand-written lines to ~4-8 declarative lines, so adding an 18th factory method is now a 5-line addition instead of a 20-line ceremony. That was the whole point.

**Landmines defused**:
- TypeScript's eager-vs-lazy generic inference asymmetry. Schema-style generic helpers force eager resolution of their type parameters, which can trigger circular-type errors in places where inline arrow-function bodies would have been fine. Explicit return-type annotations on the `build` callback restores lazy resolution. Save this trick for future mixin-heavy refactors.
- Vitest's module-eval doesn't tolerate the Factory cycle even when bundled builds do. Any test file imported from `factory/` that transitively pulls `display/Container` will fail to load. Direct source-file imports (`../../utils/object` instead of `../../utils`) break the chain; alternative is co-locating resolvers in a side file.
- `as readonly string[]` casts on the `ConfigKeys` constants are needed because `ContainerConfigKeys: (keyof ContainerConfig)[]` is a mutable array of literal unions, and the schema's `exclude?: readonly string[]` is a readonly string array. TypeScript's variance rules reject the direct assignment but the cast is safe because the helper only reads the array.
